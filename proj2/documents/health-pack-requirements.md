# 血包（苹果）玩法需求规格

> 状态：已批准；实现 gate 见 `PHASE_2DOT5_SPEC.md`  
> 目标读者：负责实现、评审和验收该机制的开发者  
> 文档目的：锁定跨楼层血量与苹果血包的玩法语义、边界和验收条件；不规定逐文件施工顺序。

## 1. 需求摘要

玩家进入下一层时应保留当前生命值，不再自动恢复为初始生命值。每层地牢生成若干苹果作为一次性血包；苹果数量由当前难度的配置范围决定，且不得生成在玩家出生房间或楼梯所在房间。

苹果是当前玩法中的地图资源，不属于背包物品。玩家缺血时走到苹果所在格会立即恢复生命值，随后苹果从地图消失。

## 2. 问题与动机

当前换层逻辑会重新创建 `Player`，新对象从 `GameConfig.playerHp` 获得初始生命值。因此，上一层战斗造成的生命损失不会延续到下一层，楼层之间缺少资源消耗压力。

引入跨层血量和有限血包后：

- 战斗损失会影响后续楼层；
- 探索非关键房间能够带来恢复收益；
- 玩家出生后不能立即获得血包；
- 玩家前往楼梯时不能顺便稳定获得血包；
- 不同难度可以通过配置调整恢复资源的稀缺程度。

## 3. 目标与非目标

### 3.1 目标

- 玩家换层前后的当前生命值保持一致。
- 每层苹果数量在配置的闭区间内确定性随机生成。
- 苹果只生成在房间内部的普通可行走地板上。
- 玩家出生房间和楼梯房间内不生成苹果。
- 苹果不与玩家、敌人、楼梯或其他苹果重叠。
- 玩家拾取苹果后获得治疗，生命值不超过上限。
- 保存和加载后，玩家生命值与剩余苹果状态保持一致。
- 相同 seed、楼层、难度和配置得到相同的初始苹果数量与位置。

### 3.2 非目标

- 不建立通用背包、物品栏、掉落表或装备系统。
- 不让敌人拾取、守卫、争夺或破坏苹果。
- 不把苹果作为独立 Agent 工具或战术目标。
- 不修改跨进程 Agent 协议来暴露苹果类型。
- 不围绕遗留的 `Game.playWithInputString(String)` 增加运行时或测试能力。
- 不改变玩家攻击蓄力、伤害、敌人生成或楼层难度增长规则。

## 4. 当前实现约束

以下内容是实现本需求时必须考虑的当前事实：

- [`Game.nextFloor()`](../byog/Core/Game.java) 会为新楼层创建新的 `Player`，因此当前生命值会被重置。
- [`WorldGenResult`](../byog/WorldGen/WorldGenResult.java) 已提供当前楼层的房间列表。
- [`SquareRoom.getFloorPositions()`](../byog/WorldGen/SquareRoom.java) 已提供房间内部的地板坐标。
- [`Game.placeStairs()`](../byog/Core/Game.java) 当前只修改 world tile，不返回楼梯坐标或楼梯房间。
- [`EntityManager`](../byog/Entity/EntityManager.java) 把实体作为占位物处理；可拾取苹果不适合直接作为普通 `Entity`。
- [`GameSaveData.extraData`](../byog/IO/GameSaveData.java) 可以保存新增机制的可序列化状态。
- [`VisibleTile`](../byog/Perception/VisibleTile.java) 当前没有苹果类型；未知 tile 会映射为 `UNKNOWN`。

## 5. 玩法规则

### 5.1 跨楼层生命值

玩家进入下一层时，新楼层中的当前生命值必须等于进入楼梯前的当前生命值。

本需求只锁定生命值语义。攻击力、蓄力、受击动画计时等其他玩家状态沿用现有换层行为，除非后续需求另行规定。

### 5.2 苹果表现与占位

- 苹果使用独立的可见 tile，例如 `Tileset.APPLE`。
- 苹果优先使用本地 16×16 emoji 风格图片；图片不可用时显示红色 `●`，description 为 `apple health pack`。
- 苹果所在格必须可行走，不能阻挡玩家或敌人移动。
- 苹果只生成在 `SquareRoom` 的内部地板，不生成在墙、走廊、楼梯或虚空上。
- 苹果不是实体，不进入 `EntityManager` 的位置索引。
- 敌人站在苹果格上时不会拾取或销毁苹果；实体渲染可以暂时覆盖底层苹果，实体离开后苹果仍存在。

### 5.3 生成数量

每个难度配置以下字段：

```properties
easy.healthPack.minCount=3
easy.healthPack.maxCount=5
easy.healthPack.healAmount=25

balanced.healthPack.minCount=2
balanced.healthPack.maxCount=4
balanced.healthPack.healAmount=20

hardcore.healthPack.minCount=1
hardcore.healthPack.maxCount=3
hardcore.healthPack.healAmount=15
```

以上数值是首轮建议值，可在试玩后调整。字段行为必须满足：

- `minCount >= 0`；
- `maxCount >= minCount`；
- `healAmount > 0`；
- 实际目标数量从 `[minCount, maxCount]` 中均匀选取，包含两端；
- 缺失或非法配置使用代码内安全默认值，并通过 `Logger` 记录回退原因。

### 5.4 生成位置

生成器应先确定玩家出生位置、楼梯位置和敌人初始位置，再从剩余候选格中选择苹果位置。

候选格必须同时满足：

1. 位于某个房间的内部地板；
2. 不属于玩家出生位置所在房间；
3. 不属于楼梯所在房间；
4. 当前 tile 是普通地板；
5. 没有玩家或敌人占用；
6. 尚未被其他苹果选中。

“排除房间”表示排除整个房间内部，而不是只排除玩家或楼梯所在的单个坐标。

当合格位置少于目标数量时，生成所有可用苹果即可。游戏不得因候选格不足而失败或无限重试，并应通过 `Logger` 记录实际生成数量低于目标数量。

### 5.5 确定性随机

苹果生成必须使用独立随机流，避免影响房间、楼梯、敌人或战斗的现有随机序列。推荐的随机种子组成如下：

```text
game seed + floor id + health-pack namespace
```

候选位置在随机选择前必须具有稳定顺序，不能依赖 `HashSet` 或 `HashMap` 的遍历顺序。

### 5.6 拾取与治疗

- 只有玩家能够拾取苹果。
- 玩家当前生命值低于生命值上限时，进入苹果格立即恢复 `healAmount`。
- 治疗后的生命值不得超过生命值上限。
- 当前实现暂以当前难度的 `player.hp` 作为生命值上限。
- 成功治疗后，苹果 tile 恢复为普通地板。
- 玩家满血时进入苹果格不会消耗苹果；离开该格后苹果仍应显示并可在之后拾取。
- 拾取结果通过 `Logger` 记录，至少包含恢复量和治疗后的生命值。

## 6. 楼层生成流程边界

新游戏和进入下一层应遵守同一套苹果生成规则。概念顺序如下：

```text
生成房间与走廊
→ 确定玩家出生位置
→ 确定楼梯位置和楼梯房间
→ 生成并登记敌人
→ 排除玩家房、楼梯房和实体占位
→ 生成苹果
→ 开始该楼层的游戏循环
```

读档不是一次新的楼层生成。读档应恢复存档中的剩余苹果，而不是重新掷一次数量和位置。

## 7. 存档与开发期兼容策略

### 7.1 必须保存的状态

存档至少保存：

- 玩家当前生命值；
- 当前楼层剩余苹果的坐标；
- 解释这些坐标所需的楼层身份信息继续沿用现有 `seed` 和 `floorLevel`。

读取存档后：

- 已拾取的苹果不得重新出现；
- 未拾取的苹果必须回到原坐标；
- 玩家满血经过但未消耗的苹果必须继续存在。

### 7.2 旧存档

DungeonMind 仍处于开发阶段，本需求与 Phase 2.5 不提供旧存档迁移。缺少正式玩家整局状态、剩余苹果、
敌人朝向或其他新格式必填字段的存档应拒绝加载；不得临时重掷苹果，也不得用默认值拼出半恢复世界。

加载失败时保留原文件，通过 `Logger` 记录明确路径并返回命名世界列表。程序不自动删除；由开发者自行处理
无法继续使用的旧文件。现有单文件 `save/game.ser` 不迁移到命名世界目录。

## 8. Agent 与感知边界

本需求不让 Agent 理解或利用苹果。苹果机制本身不向 Agent contract 增加字段。Phase 2.5 会因敌人朝向与
视野规则整体升级 Observation，但苹果在新契约中仍必须保持隐藏：

- `VisibleTile.tileTypeOf()` 应把苹果映射为 `FLOOR`；
- 苹果仍按普通地板参与可行走性判断；
- 不新增 Agent skill、world event、message type 或 protocol schema 字段。

未来如果玩法要求敌人识别、守卫或争夺苹果，应另写需求，并通过版本化 Observation 和技能契约接入，不能直接向 Agent 暴露 live world。

## 9. 失败处理

| 情况 | 预期行为 |
|---|---|
| `minCount` 小于 0 | 使用安全默认值并记录配置错误 |
| `maxCount` 小于 `minCount` | 使用安全默认范围并记录配置错误 |
| `healAmount` 不大于 0 | 使用安全默认值并记录配置错误 |
| 没有合格房间 | 生成 0 个苹果，游戏继续 |
| 合格位置少于目标数量 | 生成所有合格位置，游戏继续 |
| 无法识别玩家房或楼梯房 | 不在该楼层生成苹果，避免违反排除规则 |
| 旧存档没有苹果状态 | 拒绝该存档，保留文件并记录路径，不迁移或重掷 |

游戏运行期间的相关控制台信息必须通过 `Logger` 输出。

## 10. 验收条件

实现满足以下条件时，本需求可以验收：

1. 玩家以任意非零生命值进入下一层后，生命值保持不变。
2. 每层初始苹果数量位于当前难度配置的闭区间内。
3. 同一 seed、楼层、难度和配置重复生成时，苹果数量与位置完全一致。
4. 所有苹果均位于房间内部普通地板，位置互不重复且不与实体重叠。
5. 玩家出生房间和楼梯房间内的苹果数量均为零。
6. 缺血玩家拾取苹果后按配置恢复生命值，且不超过生命值上限。
7. 满血玩家经过苹果不会消耗苹果。
8. 保存并重新加载后，玩家生命值和剩余苹果的位置不变，已拾取苹果不会复活。
9. 非法配置和候选位置不足不会导致崩溃、卡死或无限循环。
10. 苹果的加入不改变既有地图、楼梯、敌人和战斗随机序列。
11. Agent Observation 与 wire contract 不因本需求新增字段或消息类型。

## 11. 方案取舍

### 11.1 选择 tile，而不是普通实体

普通实体会参与位置占用和碰撞，玩家无法自然走入其格子。苹果作为底层可行走 tile 能复用现有渲染和移动模型，改动范围更小。

代价是拾取逻辑仍需在玩家移动提交后检查底层 tile；未来如果物品类型显著增加，应评估独立的地图物品层，而不是持续扩大 tile 常量和条件分支。

### 11.2 保存剩余苹果，而不是只依赖 seed 重建

seed 可以重建苹果的初始位置，但无法表示哪些苹果已经被拾取。只在读档时重新生成会产生重复治疗资源，因此存档必须记录当前剩余苹果。

### 11.3 暂不暴露给 Agent

当前需求的目标是建立玩家的跨层恢复资源。让 Agent 理解苹果会扩大 Observation、协议、记忆、规划和验证范围，且目前没有对应玩法收益，因此暂不纳入。

## 12. 已锁定默认值与未来边界

- Easy、Balanced、Hardcore 使用 §5.3 的首轮数量范围和 `healAmount`；试玩后调整必须通过配置，不改变规则语义。
- Phase 2.5 继续以当前难度的 `player.hp` 作为生命上限，不新增可成长的 Player `maxHp`。
- 未来若引入生命上限成长，`maxHp` 属于整局 `PlayerRunState`，不能只放在当前楼层快照。
- 苹果优先使用 16×16 emoji 风格图片，字符 fallback 为红色 `●`、黑色背景、description `apple health pack`。
