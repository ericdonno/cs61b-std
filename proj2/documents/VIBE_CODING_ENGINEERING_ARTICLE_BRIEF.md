# Vibe Coding 工程化文章写作提纲

> 文档用途：固定文章角度、读者、结构、项目证据和表达边界，供后续写作使用。
>
> 它不是项目事实底稿、README、最终博客或宣传文案。项目事实以
> [`PROJECT_WRITING_MATERIALS.md`](../PROJECT_WRITING_MATERIALS.md) 为准；本文不得反向覆盖事实底稿。

## 1. 文章定位

这是一篇由 DungeonMind 真实开发经历驱动的 Vibe Coding 工程实践文章。文章先提炼可复用的方法，再用技术案例
验证其作用，最后讨论人的职责、理解与判断。它不按项目提交或工程阶段逐项复述，也不要求读者预先了解游戏。

### 目标读者

核心读者是已经使用 Codex、Claude Code、Trae 等 Coding Agent 开发真实项目，并开始遇到需求漂移、架构膨胀、
文档过量或项目理解困难的个人开发者和小团队工程师。

本文不以以下读者为主要对象：只想了解 DungeonMind 玩法的人、Coding Agent 入门用户、招聘者，以及只讨论抽象
人机关系而不关心工程实践的人。

## 2. 核心矛盾

项目先后出现了两种不同瓶颈：

1. Trae + DeepSeek 阶段的生成代码仍在作者可阅读范围内，但现有模型和工作流无法继续设计 LLM AI。
2. 引入 Codex 与结构化文档工作流后，LLM AI 被拆成可以实施和验证的工程阶段；随后，Agent 生成的架构和文档
   超过作者的阅读能力，作者后期基本直接信任 Codex 的判断。

全文围绕这一变化展开：

> 问题先是 Agent 无法把项目继续设计下去，后来变成 Agent 可以持续推进，而人逐渐看不过来。

文章不应把第二个问题包装成已经解决。文档整理改善了位置、权威级别和检索入口，尚未解决有限阅读时间下的理解
与审查问题。

## 3. 建议结构

### 一、两次完全不同的瓶颈

只提供理解后文所需的最小背景：

- CS61B Project 2 Phase 1 由作者手写；
- Trae + DeepSeek 完成后续明确功能、传统 AI 和本地 AI；
- `early-dungeonmind-build-guide` 到感知层开始失去有效指导，代码构建和游戏设计逐渐失去方向；
- 准备设计 LLM AI 时，作者判断旧模型与工作流已经触顶，转而引入 Codex、Grilling skill 和 GPT-5.6-sol；
- 新工作流恢复了推进能力，也产生了新的信息与理解负担。

这里不得改写成“Trae 阶段代码生成速度超过 review 带宽”。

### 二、把想法变成 Agent 可以执行的工程约束

把五类文档写成一条控制链，而不是五份文件的功能清单：

```text
Intent
→ Roadmap
→ Phase Spec
→ Build Guide
→ Implementation
→ Completion
```

- Intent 固定项目为何存在以及不可牺牲的目标；
- Roadmap 固定阶段、依赖和推进顺序；
- Spec 固定当前阶段做什么、不做什么以及验收条件；
- Build Guide 把阶段目标转换成 Agent 可以执行的施工顺序；
- Completion 保存实际命令、结果、未验证项和下一阶段的前置事实。

该链条是 DungeonMind 中逐步形成的工作方法，不宣称是所有项目都必须采用的行业标准。

### 三、技术案例：约束如何进入系统

优先使用一条普通读者也能理解的完整因果链，而不是枚举项目架构：

```text
敌人不应作弊
→ 只能依据私有感知作决定
→ Java 保持世界状态和动作合法性的唯一权威
→ 外部 Agent 只接收裁剪后的 Observation
→ contract、fixture 和测试验证信息与动作边界
```

这条案例用于说明产品意图如何依次转化为不变量、架构边界、协议和验证证据。异步双速、过期意图、独立 Session
等机制只在帮助解释同一论点时补充，不展开成完整架构介绍。

### 四、当工程约束本身变成新的复杂度

先分开说明两类复杂度，再讨论它们如何叠加：

1. **系统复杂度**：私有感知、跨进程协议、异步 Agent、状态管理和测试体系带来的实现与运行成本；
2. **信息复杂度**：大量文档、历史方案、重复说明和不同权威级别带来的阅读与维护成本。

项目已经完成过一次文档整理：迁移和分类 40 份文档，对 59 个 Markdown 做链接与结构检查。这证明信息架构可以
被治理，但不能证明作者已经读完或掌握全部内容。

Mermaid 对理解局部结构有效：作者花费较长时间后，能够理解一张复杂的 AI tick 图。困难来自完整架构需要许多张
同等复杂的图，累计阅读成本过高；模型也不能自动发现作者的知识缺口并安排最短理解路径。后期作者基本直接信任
Codex；这一事实可以用于说明理解方式发生了变化，但在没有具体事故证据时，不得写成直接信任已经导致工程失败。

### 五、尚未闭环的第二层约束

讨论一种仍待项目验证的治理方向：

- 新增机制必须对应已经说明的问题或瓶颈；
- 区分“值得考虑的风险”和“本轮值得实现的需求”；
- 必要复杂度可以保留，但应尽量集中封装，并保持核心执行路径和核心阅读路径清晰；
- 文档同样需要职责、权威级别、生命周期和退出位置；
- 思考可以广泛，实施应选择最小充分解。

Ponytail 可以作为上述原则的代表性例子，使用 “Explore broadly. Implement narrowly.” 概括其倾向。但 DungeonMind
没有明确的使用前后对照，不能声称 Ponytail 已经缩小某项设计、减少多少代码或解决了文档膨胀。GitHub 星数和
“最高星 Skill”也不是文章论证所必需的事实。

### 六、作者观点：职责上移不等于能力自然上移

作者在项目中同时承担了产品方向、阶段与范围管理、技术边界裁决、部分开发和最终验收等职责。Vibe Coding 使工作
重心从逐项实现上移到目标、约束、取舍和验收，但项目经历同时表明：Agent 产量提高不等于作者理解能力同步提高。

结尾保留真实的未解决状态：

> 更强的模型和工作流扩展了个人能够推进的项目规模，也制造了新的认知债务；DungeonMind 尚未形成一套能够证明
> 作者在有限时间内持续掌握关键系统事实的方法。

不写成“人已经通过高层管理完全掌控项目”，也不把潜在的能力退化写成已经证实的长期结果。

## 4. 证据分配

| 文章论点 | 优先证据 | 表达限制 |
|---|---|---|
| 旧模型与工作流在 LLM AI 设计处触顶 | 作者陈述；早期 Build Guide；开发历史 | 不能写成代码看不过来 |
| 结构化工作流恢复项目推进 | Intent、Roadmap、Spec、Build Guide、Completion；Phase 0–4 实现与测试记录 | 不能声称完整多 Agent 游戏已经完成 |
| 产品意图转化为技术边界 | Java 权威、Observation、wire contract、相关 tests | 只选择足以支撑论点的细节 |
| 真实外部 provider 已发生交互式调用 | 2026-09-06 运行日志截图；作者确认 | 单次运行不等于正式阶段验收或完整 MVP 完成 |
| 文档和架构超过作者阅读能力 | 作者陈述；文档规模与整理记录；Mermaid 尝试 | 不能把主观困扰直接写成已发生事故 |
| Ponytail 提供复杂度治理思路 | Ponytail 规则；作者后续认识 | 无项目内前后对照，不写成成果 |
| 人的职责发生上移 | 作者陈述；阶段裁决和 Completion 记录 | 同时披露后期基本信任 Codex 的事实边界 |

## 5. 暂定标题

主标题优先考虑：

> 当 Agent 终于能把项目做下去，我却开始看不过来了

解释性副标题：

> DungeonMind 中一次 Vibe Coding 工程化的实践与代价

标题不使用“最佳实践”“完整方法论”“成功治理”或“最高星 Skill”等未经项目结果支持的表述。
