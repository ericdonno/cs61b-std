# Build Guide Writer

把 Build Guide 写成给人施工的教学文档，不要写成 Spec 的缩写、类名清单或作者的改动日志。

目标读者可能会写代码，但没有做过同等工程复杂度的项目。解释本阶段新出现的工程概念和逻辑，同时尊重读者已经具备的基础，不要把文档写成语言入门教程。

## 1. 先确定文档契约

开始写作前完成以下调查：

1. 读取项目级指令和文档生成约束。
2. 读取本阶段 Spec、Roadmap 中相关部分和架构决策文档。
3. 读取上一阶段 Build Guide，提取读者已经熟悉的术语、代码结构和写作节奏。
4. 检查当前代码和文件树，区分：
   - 已存在并要修改的文件；
   - 本阶段要新建的文件；
   - 已废弃或明确禁止依赖的入口；
   - 用户已有且必须保留的编辑。
5. 明确读者起点、阶段终点、范围外事项和最终验收证据。

如果 Spec 与代码、Roadmap 或旧 Guide 冲突，先指出冲突并以项目规定的 source of truth 为准。不要在 Guide 中偷偷替项目做新的架构决策。

## 2. 保持 Guide 与 Spec 的分工

把两类文档写出明显区别：

| Spec 回答 | Build Guide 回答 |
|-----------|------------------|
| 必须满足什么契约 | 为什么现在需要这个契约 |
| 字段、接口和状态的精确定义 | 它应放在哪里、如何逐步接入 |
| 测试 ID 和验收断言 | 如何构造场景、观察什么现象 |
| 边界和禁止事项 | 初学者最可能怎样误解或写错 |

不要逐段改写 Spec。可以引用 Spec 的章节、接口和测试 ID，但要补上实现顺序、因果解释、具体场景和排错路径。

如果 Spec 使用 `Step N.x`，Guide 默认保持 `N.x` 一一对应。需要改变顺序时，显式解释原因并给出映射表，不能让编号看似对应、内容实际错位。

## 3. 先从上一阶段建立心智模型

不要直接从“创建某类”开始。先回答：

1. 上一阶段现在怎样运行？
2. 新需求为什么使旧结构不再够用？
3. 如果直接用最直觉的方案，会出现什么具体故障？
4. 本阶段用什么核心结构解决？
5. 一次完整数据流或控制流怎样走完？

优先使用读者已经认识的旧入口作为起点：

```text
旧调用链
  → 新问题出现的位置
  → 新组件插入的位置
  → 新的完整调用链
```

只在能降低理解门槛时使用类比。一个贯穿全文的类比胜过每段一个新比喻；类比之后必须回到真实类、字段和调用顺序。

## 4. 分开解释“新概念”和“新逻辑”

### 4.1 解释新概念

概念首次承担重要作用时，按以下顺序解释：

1. **它是什么**：用一句普通话定义。
2. **为什么现在出现**：说明上一阶段为何不需要、本阶段为何必须需要。
3. **它归谁负责**：指出所属类、线程、状态组或模块。
4. **它不是什么**：消除最可能的混淆。
5. **一个具体例子**：给出小型对象、消息或时间线。

例如，不只写“加入 backpressure”，还要解释：

```text
生产者和消费者速度不同
  → 无界队列会一直增长
  → 有界队列满时必须合并、丢弃或拒绝
  → 这套压力传递规则叫 backpressure
```

避免先堆积一整页术语表再进入正文。优先在第一次真正使用时解释。若一段固定流程连续引入多个短术语，可在流程后放一个紧凑名词表，只列该流程中出现且用户要求解释的词，不擅自扩充成词典。

### 4.2 分析新逻辑

逻辑解释必须覆盖“顺序”和“因果”，不能只描述最终结构：

- 谁先执行，谁后执行；
- 状态在哪一步改变；
- 数据在哪一步成为权威；
- 失败时保留什么、作废什么；
- 为什么相邻两步不能交换；
- 并发或迟到事件在什么安全边界生效。

对复杂逻辑至少给出一个带具体值的完整案例，例如：

```text
tick 41 发出 request generation 5
tick 42 本地反射接管
tick 43 收到基于旧观察的响应
完整身份仍匹配，但当前前提已失效
因此 Validator 拒绝，旧队列和 cooldown 不变
```

复杂状态机同时提供：

- 状态各自只描述什么；
- 正常状态组合；
- 关键转换时间线；
- 一个最容易误判的失败案例。

## 5. 按垂直切片安排施工顺序

使用可以独立编译和验证的垂直切片，不要按“先写完所有数据类、再写完所有网络类”横向堆积。

每个阶段只解决一个主要风险，并明确暂时不碰什么：

| 阶段 | 本阶段闭环 | 暂时不碰 | 阶段闸门 |
|------|------------|----------|----------|
| N.1 | 可独立证明的小能力 | 下一层复杂度 | 对应测试 |

优先顺序通常是：

1. 固化纯数据和边界。
2. 在外部依赖关闭时完成本地骨架。
3. 用 fake clock、fake transport 或 fake service 完成状态核心。
4. 再接真实 IO 或外部进程。
5. 最后做生产集成、故障演练和交接证据。

这样每次失败都能定位到刚加入的一层。

## 6. 使用统一的小节模板

每个主阶段先写：

```markdown
## N.x 阶段名称

> **一句话目标**：完成后能观察到或断言什么。
```

每个子任务按需要使用以下骨架：

```markdown
### N.x.y 子任务

**做什么**：要创建或修改什么。

**解释**：新概念是什么，为什么需要。

**怎么做**：文件、职责、顺序、参数和伪代码。

**为什么不能直接……**：解释最诱人的错误方案。

**验证**：给出动作、输入和可观察结果。
```

不必机械地显示全部标签，但内容不得缺少“为什么”“怎么做”和“如何确认”。对同一文件的多个改动，可用“位置一/二/三”集中说明，避免读者在文档中来回跳。

阶段末尾必须有阶段闸门：

```markdown
### N.x 阶段闸门

- [ ] 可观察行为或精确断言
- [ ] 对应测试通过
- [ ] 上一阶段回归未改变
```

闸门应描述证据，不要写“功能正常”“代码完成”。

## 7. 控制代码、表格和图示的密度

使用代码块表达以下内容：

- 稳定接口形状；
- 关键数据结构；
- 调用顺序；
- 状态转换；
- 容易发生 off-by-one 或竞态的伪代码。

不要粘贴整类实现。Build Guide 应告诉读者如何思考和组织实现，而不是提供无法理解的复制品。

使用表格处理精确映射：

- 文件与职责；
- 状态与含义；
- 消息方向；
- 配置及默认值；
- 故障模式、期望行为和证据；
- Spec Step 与 Guide 阶段。

只有在关系确实难以线性说明时才画图。优先使用最小 ASCII 数据流或时间线，不为装饰添加复杂架构图。

## 8. 为初学者提供真实施工抓手

每个阶段尽量回答：

- 从哪个现有方法或文件开始看；
- 新类放在哪个 package；
- 哪些字段必须不可变；
- 哪个线程允许调用哪个方法；
- 哪个 tick 阶段读写该状态；
- 一个方法返回值究竟证明了什么；
- 最小测试怎样构造；
- 出错时先看哪个状态或 trace。

明确区分：

- “消息已进入本地队列”与“远端已收到”；
- “JSON 语法合法”与“业务 schema 合法”；
- “连接恢复”与“远程控制已安全接管”；
- “动作已提出变化”与“世界已 commit”；
- “测试 fake”与“生产实现”。

这些边界比额外罗列类名更能帮助初学者。

## 9. 保持工程边界和诚实性

- 不让 Guide 引入 Spec 范围外的框架、依赖或未来阶段功能。
- 不围绕项目已经废弃的 API 建新生产路径。
- 不把“可选外部 runtime”写成默认启动的硬依赖。
- 不宣称尚未运行的测试已经通过。
- 不自动覆盖 golden 或修改基线来让回归变绿。
- 不把真实时间、随机 ID、线程名等不稳定值放进确定性证据。
- 不用无限等待或更多 sleep 掩盖并发问题。
- 不为了显得完整而虚构不存在的类、配置、命令或测试 ID。

如果文档描述的是计划中的文件，明确标注“新建”；描述现有代码时先实际检查。

## 10. 完成前执行文档级验证

一次性批量完成以下检查，避免反复扫描大文档：

1. **结构映射**
   - Guide 主阶段数量与 Spec Step 数量一致；
   - 每个阶段都有目标和阶段闸门；
   - 编号、标题和内容没有错位。
2. **契约一致**
   - API 名称、身份字段、状态名、配置 key/default 与 Spec 一致；
   - 示例中 ID 的生成方、回传方和失效规则正确；
   - tick 顺序和 commit boundary 没有矛盾。
3. **Markdown 完整**
   - 代码围栏成对；
   - 表格列数和标题层级合理；
   - 本地链接存在；
   - 无乱码、异常替换字符和非必要行尾空格。
4. **读者体验**
   - 首次出现的重要概念有解释；
   - 每段复杂逻辑至少有一个具体案例；
   - 验证步骤能操作和观察；
   - 排错表使用“现象 → 原因 → 第一检查点”。
5. **变更边界**
   - 只修改用户要求的文档或 skill；
   - 保留无关工作区改动；
   - 未经请求不暂存、不提交。

文档任务通常不需要编译代码。只有在 Guide 同时修改了代码、命令可低成本验证，或用户明确要求时才运行项目测试；否则报告完成的是文档一致性检查。

## 11. 推荐的最终结构

根据项目复杂度裁剪，不机械追求篇幅：

```text
标题与一句话定位
先读这里 / 阅读方法
文档分工与范围外事项
不可破坏的工程边界
从上一阶段到本阶段的心智模型
关键数据流、tick 顺序或状态模型
实施路线与阶段映射
N.1～N.x 分阶段施工
文件导航
验证命令
常见问题与排错顺序
最终验收清单
```

以“读者能独立完成并知道自己为什么这样做”为完成标准，而不是以字数、代码块数量或覆盖所有术语为标准。
