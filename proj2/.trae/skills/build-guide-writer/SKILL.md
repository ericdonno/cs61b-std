# 分阶段构建指南写作规范

本 skill 定义了如何撰写高质量的分阶段技术构建指南（build guide）。参考范例：DungeonMind_Build_Guide.md。

---

## 写作原则

构建指南不是"我做了什么就写什么"的记录，而是"读者需要知道什么、会困惑什么、在什么时候需要确认什么"的引导。

---

## 结构规范

### 0. 文档头部

```markdown
# <项目名>

> 一两句话说清楚这个文档是干什么的，读者读完能建成什么。
> 
> **阅读建议**：如果你对整体架构还不熟悉，建议先读"架构概览"。
```

### 1. 架构概览（必选）

在动手写代码之前，先给读者一张地图。

- 用 ASCII 框图展示分层结构，每层标注"它回答什么问题"
- 用一句话描述数据流向
- 解释核心设计理念（1~2 个关键概念即可）

**写出给人记忆锚点，不是给全貌。** 读者不需要记住每个类名，但需要知道"有四层，数据从感知层流向执行层"。

### 2. 前置准备

**文件清单表**：每个阶段新建/修改什么文件，用表格一目了然。

**预判坑点**：把整个项目中最容易踩的 2~3 个坑提前说清楚（现象 + 原因 + 正确做法），而不是让读者在阶段中撞了再救。

### 3. 每个阶段

每个阶段遵循固定模板：

```
## 阶段 N：<名称>

> **一句话目标**：<具体可观察的验收画面>

### N.1 <子任务>

**做什么**：<一句话说清楚目的>

**解释**：<为什么需要、它是什么、核心原理。用比喻降低门槛。>

**怎么做**：<具体步骤，参数给数字，不给含糊词>

**验证**：<可操作可观察的确认方式>
```

**"一句话目标"的写法**：不说"实现 XX 功能"，而是描述一个**用户能看到/感知到的画面**。
- 好：`屏幕上看得到红色 'E' 在随机走动，且不穿墙、不走出地图`
- 坏：`完成 Enemy 类的创建和集成`

### 4. 附录

**附录 A：常见陷阱**——用"现象 → 原因 → 正确做法"三段式：
```
现象：<用户会看到的错误表现>
原因：<根因>
正确做法：<具体修复方式>
```

**附录 B：验收清单**——纯 checkbox，每个 item 是**可观察的行为**，不说"XX 功能已实现"。
- 好：`[ ] 敌人追击路径为 BFS 最短路径，遇墙绕行`
- 坏：`[ ] BFSPathfinder 功能正常`

## 写作技巧

### 1. "做什么 → 解释 → 怎么做 → 验证" 四段式

每个小节都遵循这个骨架。缺任何一个环节都会让读者卡住：
- 缺"解释"→ 读者在抄代码，不知道自己在干嘛
- 缺"验证"→ 读者做完不确定对不对

### 2. 预判读者的"为什么"

在读者产生困惑的地方，**抢在提问之前**解释。识别方法：写完一步后问自己"如果我是读者，看到这句话会想问什么？"

典型模式：
```
<陈述一个做法>
**为什么<这样做而不是别的做法>**：<解释>
```

### 3. 参数给数字，不给含糊词

- 好：`temperature=0.7, max_tokens=500, 阈值 3 格, 冷却 30 秒, 连续失败 3 次`
- 坏：`合适的参数, 足够大, 明显偏差, 一段时间, 多次`

### 4. 好比喻降低门槛

用日常场景解释技术概念，但控制密度——只在概念最难理解的地方放比喻。
- 好：`Tileset 是游戏的"瓦片工厂"`、`GameStateSnapshot 是游戏世界的"截屏"`
- 过度：每段都有比喻，文档变成散文

### 5. "位置一/二/三"模式

当需要在**同一个文件**里改多个地方时，用"位置一/二/三"而不是分散成独立小节。这暗示读者"这些修改在同一个文件里，你要从头改到尾"。

### 6. 验收表达式

验证步骤必须是**可观察的行为**，不是"功能正常"：
- 好：`在 main 方法中手动入队几个 MoveAction → 逐一出队打印`
- 好：`玩家靠近敌人（7 格内）→ 敌人沿最短路径追击`
- 坏：`验证 ActionQueue 功能正常`

### 7. 降级信息有 checklist

验收清单的每个 item 描述一个具体的、可直接观察的测试场景，读者能逐条打勾确认进度。

### 8. 不要大代码块

优先用步骤化的文字解释如何编写代码。“build guide”的主要任务是传达思想。

如果遇到复杂的算法或核心逻辑时，必须使用结构清晰的伪代码，并配合详尽的行内注释进行原理解析。并在后面添加大量文字解释。
