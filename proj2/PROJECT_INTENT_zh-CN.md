# DungeonMind 项目意图

> 状态：产品意图基准文档
>
> 本文记录 builder 当前确认的意图。此前的 TDD、构建指南、评审和 brainstorm 文档仍是有价值的设计历史；但如果它们与本文的产品方向冲突，以本文为准。

## 1. 项目为何存在

DungeonMind 起源于 CS61B Project 2（BYOG），但它现在的首要目标，是让 builder 通过构建一个真实的游戏 AI 系统学习现代 Agent 工程。

项目应证明的不只是一次 LLM API 调用，而是一条可观察的 Agent 循环：敌人感知游戏世界，在信息受限下推理，形成意图，使用工具，通过游戏引擎行动，接收反馈，沟通，并重新规划。

技术复杂度本身并不够。Agent 系统最终必须让地牢游戏对玩家更有趣、更沉浸，并能产生更丰富的策略。

## 2. 产品愿景

玩家扮演一名不断深入程序生成地牢的冒险者。每一层都有少量敌人或守卫，它们拥有不同能力和一定的战术素养。

敌人不是全知全能的障碍物；它们与玩家同样存在于游戏世界中：

- 它们通过自己的视觉、听觉、受伤以及收到的消息了解事件；
- 它们持有不完整的信念，因此可能犯合理的错误；
- 它们能够巡逻、调查、搜查、战斗、撤退、警告盟友、拉响警报，并通过实际行动操作地牢设施；
- 它们可以组成小队、协同行动，但协作必须由独立敌人之间的通信产生；
- 玩家能观察其行为、推断其战术意图，并通过欺骗、绕行、分割或直接战斗来应对。

期望的体验是一场围绕信息与战术的对抗，而不是与一个看不见的全知控制器对抗。

## 3. Agent 身份与边界

每个敌人都是独立的 Agent，分别拥有：

- 感知；
- 信念状态；
- 工作记忆；
- 目标和当前意图；
- 决策过程；
- 行动与通信历史。

不存在共享意识，也不存在一个 LLM 意识同时控制一群敌人的身体。

小队行为和警报扩散必须经由世界内机制发生，例如呼喊、信号、警报、直接接触或其他明确的通信行为。如果敌人被杀、被隔离、被打断，或无法通信，那么它没有传递出去的信息不会自动被盟友知晓。

敌人不应自动知道：

- 玩家未被它感知、也未被报告时的当前位置；
- 玩家未被观察到的生命值、背包、能力或意图；
- 未经通信的远方盟友的观察或状态；
- 已死亡且未传递信息的敌人掌握的情报；
- 仅仅因为游戏引擎持有，就能得知权威性的全局游戏状态。

敌人可以对未知事实作出推断，但推断应保持不确定，也应能被玩家诱导和利用。

## 4. 单层游戏循环

当前设想的一层地牢体验如下：

1. 玩家从相对安全、视野受限的区域进入未知楼层。
2. 玩家探索房间和路线，定位楼梯，并观察敌人的类型、巡逻、感知方式和通信行为。
3. 玩家选择如何取得进展：原则上，绕行、欺骗、伏击、选择性战斗和正面强攻都应可行。
4. 被发现、制造巨大声响、尸体被发现或成功拉响警报，会使附近敌人进入调查、搜查或防守状态。信息只能通过有效的世界内通信传播。
5. 楼梯始终可用，但难以安全接近。下楼需要短暂交互或安全窗口，因此玩家必须绕过、分散、禁用、孤立或击败防守力量。
6. 不要求杀光所有敌人。玩家带着资源和生命值消耗的后果进入下一层；敌人与其工作记忆随本层结束而消失。

## 5. 记忆范围

第一版不需要跨楼层的玩家画像，也不需要长期适应玩家习惯。

但它需要敌人按楼层持有的短期工作记忆，例如：

- 最后看到玩家的位置和时间；
- 听到的声音及其估计来源；
- 某条信息由谁报告；
- 不确定信息的置信度和时效；
- 被发现的尸体或已变化的设施；
- 已经搜查过的位置；
- 当前计划、执行结果与重新规划的原因。

只有当玩法和世界观为跨楼层信息持续提供了可信理由时，才重新考虑长期记忆。

## 6. Agent MVP：完成定义

Agent MVP 必须使用真实的 Agent 工程；仅能调用 LLM 并不代表完成。

它应包括：

1. **Agent runtime** —— 有状态的图运行时，例如 LangGraph；或具有循环、条件转移和反馈的等价显式工作流。
2. **独立 Agent 状态** —— 每个敌人都有私有的感知、信念、工作记忆、意图、消息历史和执行反馈。敌人可以共享模型服务，但不能共享意识或上下文。
3. **工具调用（tool calling）** —— Agent 使用受约束工具观察权威游戏状态的有限切片、查询战术可能性、通信、操作设施，并提交结构化意图。
4. **结构化输出与校验** —— 模型输出受 schema 约束；引擎校验知识来源、权限、可达性和合法性。
5. **短期记忆与 checkpointing** —— 按楼层保存的观察、消息和规划状态能够跨越多个 Agent 回合。
6. **多 Agent 消息传递** —— 信息交换必须明确、可追溯、受时间影响，并受游戏规则限制。
7. **规划与执行反馈** —— 高层意图被确定性规划器和技能系统转化；成功、受阻、目标丢失等结果返回给 Agent，并可触发重新规划。
8. **异步、事件驱动的运行** —— LLM 延迟不得阻塞游戏循环；有意义的游戏事件才触发深度思考。
9. **Tracing 与评估** —— 开发者能检查每个 Agent 感知了什么、调用了哪些工具、为何选择某个意图、耗时多久、执行是否成功、是否发生回退。
10. **可见的协同遭遇战** —— 至少有一个可重复的场景，展示独立敌人共享信息，并做出玩家可见的战术响应。

## 7. 传统规则 AI 的角色

传统 AI 是支撑系统，而不是项目最终要证明的东西。

现有的 `RuleBasedBrain` 和未来的确定性逻辑承担：

- 用于和 Agent AI 对照的基线；
- 负责移动、碰撞、战斗、寻路和紧急反应的快速反射与执行层；
- Agent runtime 或模型不可用时的回退方案。

目标层级保持为：

```text
敌人感知与信念
        -> Agent 推理与工具使用
        -> 结构化 StrategicIntent
        -> 确定性规划器 / 技能
        -> ActionQueue 与原子动作
        -> 将执行反馈返回 Agent
```

## 8. 不应只为技术标签而引入的技术

项目应在技术确实带来能力或学习价值时使用 Agent 技术，而不是把流行词当作清单。

除非之后的证据表明确有必要，以下内容不是第一版 Agent MVP 的必需项：

- 为少量按楼层保存的工作记忆引入向量数据库；
- 跨楼层的玩家画像；
- 强化学习或模型微调；
- 自动改写 prompt 或代码；
- 敌人 Agent 之间不受限制的自由对话；
- 仅为封装游戏内部工具而使用 MCP。

它们是延后考虑，而非永久禁止。只要某项技术解决了已被证实的问题，或成为明确的学习目标，就可以加入。

## 9. 尚未决定的产品问题

在可玩的原型出现前，不决定战斗、潜行、欺骗和绕行之间的最终侧重。

这个平衡应由实际游玩来决定。原型原则上应支持多种方法，之后再通过观察和试玩判断哪些方法值得获得更强的奖励与更深的系统支持。

世界观、敌人派系、专属能力、受 D&D 启发的光照、声音传播、陷阱、技能、治疗和更长期的记忆，都是可能的扩展。它们应服务于核心 Agent 体验，而不应变成彼此独立的功能清单。

## 10. 当前北极星

当玩家能够诚实地说出下面这句话时，DungeonMind 就成功了：

> 我不是在和全知的脚本战斗；我面对的是依据不完整证据感知、形成意图、沟通、协作、犯下可理解错误，并且能够被我用脑子战胜的敌人。

当实现能把这种行为呈现为一条可追踪的真实 Agent 循环，而不是把一次性 LLM 调用伪装成游戏术语时，builder 的学习目标就实现了。
