# DungeonMind Phase Spec 模板

> 用途：为单个开发阶段生成可实施、可审查、可交接的构筑契约。
>
> 禁止仅根据 Roadmap 的阶段标题填空。生成者必须先完成仓库审计，并以当前代码、测试和上一阶段证据为依据。

## 1. 必读输入与审计范围

列出生成本 Spec 时实际读取的文件、代码模块、测试、运行记录和官方技术文档。必须包括：

- `PROJECT_INTENT_zh-CN.md`
- `DEVELOPMENT_ROADMAP.md`
- 上一阶段 `PHASE_N_COMPLETION.md`（Phase 0 除外）
- 与本阶段有关的当前代码和测试
- 易变化依赖的当前官方文档

没有读取的内容不得暗示已经确认。

## 2. 阶段目标与成功定义

用一段话说明本阶段结束后，系统新增了什么可运行能力。说明它怎样推动 Agent MVP，而不是只列框架名称。

## 3. 起始事实

记录审计确认的当前事实，并附文件与行号。至少覆盖：

- 已有能力；
- 可复用接口；
- 当前失败或技术债；
- 测试与运行入口；
- 与 Roadmap 假设不一致的地方。

将“事实”“推断”“建议”分开表述。

## 6. 已锁定决定、假设与待决定项

### 已锁定决定

记录本阶段不得由实现者随意改变的接口、边界、命名或行为。

### 暂时假设

记录为推进工作所作、但可被证据推翻的假设及验证方式。

### 需要 Builder 决定

只放会改变产品体验、学习目标或跨阶段契约的问题。每项说明选项、影响和 Advisor 建议。

## 7. 目标架构与数据流

描述本阶段新增或改变的数据所有权、调用方向和生命周期。必要时画最小流程图。

必须回答：

- 谁创建数据？
- 谁可以读取和修改？
- 如何关联请求、决策、动作和结果？
- 失败、取消或过期时发生什么？
- 哪些数据会保存，何时清理？

## 8. 接口与数据契约

给出本阶段需要实现的确切类、方法、schema、枚举和关键不变量。示例必须能与当前语言和依赖版本对应。

对于跨进程或持久化格式，必须包含：

- schema/version 字段；
- 必填与可选字段；
- 身份与关联字段；
- 校验失败行为；
- 向后兼容策略。

## 10. 实施顺序

将工作拆成能够单独编译、测试和审查的小步。每一步写明：

1. 输入；
2. 具体改动；
3. 验证命令；
4. 通过后产生的 artifact。

## 11. 测试与验收矩阵

测试代码默认是供 Agent 和 CI 执行的可执行契约，不是面向 Builder 的教程。优先保证入口少、失败可定位、
fixture 可复用和运行结果确定；不要用大量注释、镜像 harness 或层层嵌套 Suite 增加上下文成本。

### 11.1 测试架构摘要

先明确以下结构：

| 项目 | 本阶段决定 |
|------|------------|
| 单一 deterministic 入口 | 一个 Suite/命令；只列 leaf test class，每个测试恰好运行一次 |
| integration 入口 | 与 deterministic Suite 分离；允许的进程、网络和有界等待 |
| shared fixture/harness | 每个场景族最多一个权威 parser、clock 和 tick coordinator |
| production seam | Game 与 harness 复用的真实调度入口；禁止测试复制生产 loop 或用反射访问私有方法 |
| golden/canonical artifact | 只用于稳定 schema、wire format 或人工审计证据 |
| 排除项 | 不确定、交互式、性能或历史测试放在哪个独立入口 |

强制约束：

- 禁止 Suite 嵌套造成重复运行；聚合 Suite 直接列 leaf test class。
- deterministic test 禁止真实网络、默认存档、GUI 和 `Thread.sleep()`。
- 默认 Agent gate 的 stdout 必须简洁；成功时压制生产 DEBUG/INFO 噪声，失败信息自身应足够定位。
- integration test 必须有总超时、进程清理和可定位的阶段状态。
- gameplay、调度和随机路径优先断言不变量，不使用完整逐步行为 golden。
- 只有对外 schema、codec 或确需字节兼容的格式才允许 byte-for-byte golden。
- 历史 baseline 可以保留为 evidence，但除非兼容性本身是产品需求，不得阻止生产架构演进。
- 测试不得在普通运行中生成或覆盖 golden。
- Test ID 必须出现在测试名、失败消息或机器可检索注释中，以便 Agent 从失败直接回到 Spec。
- 共享 harness 只控制输入、时钟和故障注入；不得重新实现 Brain、Planner、规则或提交顺序。
- 测试辅助代码出现第二份 parser、tick loop、协议 builder 或场景镜像时，必须先提取共享 fixture。

### 11.2 验收矩阵

| Test ID | 场景 | 断言 | 自动/人工 | 对应需求 |
|---------|------|------|-----------|----------|
| | | | | |

测试必须覆盖正常路径、边界、失败路径和“不应发生”的行为。对随机或 LLM 行为，区分 deterministic contract test 与统计/人工评估。

矩阵描述契约，不要求“每行一个测试类”。允许一个紧凑测试覆盖同一状态转换的多个字段，但失败必须能定位到
对应 Test ID。禁止为了让测试数量看起来完整而复制同一场景。

## 12. Observability 与运行证据

规定本阶段必须记录的 trace、日志、指标和关联字段。说明哪些字段属于 deterministic canonical evidence，哪些只是诊断信息。

不得把自由文本 reasoning 当作唯一验收证据。

## 13. 失败处理、兼容与迁移

说明：

- 新能力不可用时如何退化；
- 旧存档、旧配置或旧接口如何处理；
- 是否需要 feature flag；
- 如何避免半完成状态污染后续阶段；
- 哪些行为有意保持为 legacy baseline。

## 14. 风险与停止条件

列出最可能导致返工、作弊、不可测、性能问题或玩法误判的风险。

如果发现需要突破 Intent、Roadmap 或扩大 Phase 范围，停止实现并回到 Specification/Decision，而不是自行扩张。

## 15. Definition of Done

用可证伪的 checklist 表达。至少包括：

- [ ] 所有 In Scope 交付物存在。
- [ ] 指定自动化测试通过。
- [ ] 单一 deterministic 入口运行的测试无 Suite 嵌套和重复计数。
- [ ] 默认 Agent gate 成功输出简洁，不向上下文灌入生产 DEBUG/INFO 日志。
- [ ] 测试复用生产调度 seam，没有反射或测试专用规则副本。
- [ ] gameplay 行为没有被不必要的完整轨迹 golden 锁死。
- [ ] 固定场景或人工验收通过。
- [ ] 没有违反对应 INV 约束。
- [ ] 运行命令与结果已记录。
- [ ] 已知失败和偏差没有被隐藏。
- [ ] `PHASE_N_COMPLETION.md` 已生成。
- [ ] 下一阶段所需 artifacts 已明确交付。

## 16. 下一阶段交接

明确列出下一阶段可以依赖的：

- 稳定接口与 schema；
- 测试 fixture 与命令；
- trace 或 baseline artifact；
- 已确认设计决定；
- 未解决问题和禁止假设的事项。
